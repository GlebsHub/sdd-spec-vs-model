## 2. Архитектура: Feature-Sliced Design

### 2.1. Слои

| Слой | Что лежит |
|---|---|
| `app` | Точка входа, провайдеры (Query, Router, тема AntD), глобальные стили |
| `pages` | Маршруты: валидация параметров URL, `loader` с предзагрузкой, сборка страницы из виджетов |
| `widgets` | Крупные самостоятельные блоки страницы (таблица с панелью фильтров) |
| `features` | Пользовательские действия и сценарии (фильтрация, настройка колонок, поиск) |
| `entities` | Доменная модель: схемы, типы, API, query-ключи, хуки чтения, моки |
| `shared` | Без предметной логики: `ui` (обёртки над AntD), `api` (HTTP-клиент, `queryClient`), `lib`, `config` |

### 2.2. Импорты

- Импортировать можно **только из слоёв ниже**: `app → pages → widgets → features → entities → shared`.
- Импорт между слайсами одного слоя **запрещён**. Исключение: сущность может импортировать **типы** другой сущности.
- Внешний код импортирует слайс **только через его `index.ts`**. Глубокие импорты (`@/entities/x/model/...`) **запрещены**.
- Внутри слайса используются относительные пути.
- Направление импортов, запрет импортов между слайсами и импорт только через `index.ts` проверяет `eslint-plugin-boundaries`. Это правило линтера, а не договорённость.
- Алиас `@/` указывает на `src/`. Слой — папка `src/<слой>/`, слайс — `src/<слой>/<слайс>/`. В `shared` слайсами считаются `api`, `ui`, `config` и каждая папка `lib/<имя>`.

### 2.3. Отклонения от канонического FSD

- Слой `processes` не используется.
- Внутри слайса структура плоская, без сегментов `ui/model/api`. Роль файла определяется его зарезервированным именем (раздел 3).
- Контракты API (Zod-схемы ответов, выведенные типы, фабрики query-ключей) лежат в `shared/api/<ресурс>/`, потому что так требует спецификация. Сущность реэкспортирует их и добавляет поверх `api.ts`, `queries.ts` и хуки. Дублировать схему в сущности **НЕЛЬЗЯ**.
- `src/mocks/` (мок-бэкенд) и `src/test/` (тестовая инфраструктура) не являются слоями FSD. Продовый код их не импортирует.

## 3. Доменная модель: данные первичны

Сначала описывается модель сущности, затем её представление. Компоненты не определяют форму данных.

Файлы сущности:

| Файл | Назначение |
|---|---|
| `schema.ts` | Zod-схемы ответа API и параметров запроса. Источник истины |
| `types.ts` | Типы, выведенные из схем через `z.infer`. Вручную дублировать типы **НЕЛЬЗЯ** |
| `api.ts` | Функции запросов. Ответ **обязательно** проверяется схемой (`Schema.parse`) на границе |
| `queries.ts` | Фабрика query-ключей и `queryOptions` / `infiniteQueryOptions` |
| `use<Name>.ts` | Хуки чтения и мутаций, по одному на файл |
| `mocks.ts` | Фабрики тестовых данных (faker с фиксированным seed), если они нужны тестам сущности |
| `index.ts` | Публичный API |

Компоненты никогда не вызывают HTTP-клиент напрямую. Им доступны только хуки и `queryOptions` из `entities`.

Мок-бэкенд на MSW готов и лежит в `src/mocks/`. Его хендлеры используются **и** в dev-режиме, **и** в тестах, поэтому UI разрабатывается и тестируется без бэкенда на одном и том же контракте. Менять `src/mocks/` **НЕЛЬЗЯ**: это контракт бэкенда. Для отдельного теста допускается `server.use(...)` с собственным хендлером.

## 4. Серверное и клиентское состояние

### 4.1. Где хранится состояние

| Состояние | Где хранится | Почему |
|---|---|---|
| Данные с сервера | Только кэш TanStack Query | Один источник истины, кэш, дедупликация, повтор запроса |
| Фильтры, сортировка, поиск | Параметры URL | Можно поделиться ссылкой, состояние восстанавливается при «назад», переживает перезагрузку |
| Видимость, порядок и ширина колонок | `localStorage` (настройка конкретного пользователя) | Нужна между сессиями, но не должна попадать в ссылку |
| Позиция прокрутки списка | Механизм scroll restoration роутера | Восстанавливается при «назад» |
| Открыт ли попап, ввод до debounce | `useState` в ближайшем компоненте | Локально |
| Общее состояние несвязанных компонентов, которое не подходит под строки выше | Zustand-стор в слайсе `features` | Последний вариант |

Правила:
- Копировать серверные данные в `useState` или стор **НЕЛЬЗЯ**. Производные данные вычисляются при рендере или через `select`.
- Дублировать параметры URL в сторе **НЕЛЬЗЯ**. URL — единственный источник истины для фильтров и сортировки.
- Состояние держится как можно ниже в дереве и поднимается только тогда, когда это действительно нужно.

### 4.2. Query-ключи

- Ключи создаются фабрикой сущности. Писать ключи вручную в компонентах **НЕЛЬЗЯ**.

  ```ts
  export const customerKeys = {
    all: ["customers"] as const,
    lists: () => [...customerKeys.all, "list"] as const,
    list: (params: CustomerListParams) => [...customerKeys.lists(), params] as const,
    detail: (id: string) => [...customerKeys.all, "detail", id] as const,
  };
  ```

- Ключ содержит **все** параметры, от которых зависит ответ. Это проверяет `@tanstack/query/exhaustive-deps`.
- Инвалидация делается по префиксу (`customerKeys.lists()`), а не по точному ключу.
- `staleTime` и `gcTime` задаются явно в `queryClient`. `gcTime` должен быть больше времени, на которое пользователь типично уходит со списка, иначе при возврате кэша уже не будет.

### 4.3. Хуки

Хук возвращает предметные поля, а не сырой результат `useQuery`. Деструктуризация через `...rest` **запрещена**.

```ts
export const useCustomer = (id: string) => {
  const { data, isPending, isError } = useQuery(customerQueries.detail(id));
  return { customer: data, isPending, isError };
};
```

## 5. Таблицы

### 5.1. Основа

- Логика таблицы строится на TanStack Table (headless). Элементы управления и состояния (`Input`, `Select`, `DatePicker`, `Dropdown`, `Checkbox`, `Empty`, `Spin`, `Result`) берутся из Ant Design.
- Сортировка и фильтрация выполняются на сервере: `manualSorting: true`, `manualFiltering: true`. Состояние сортировки и фильтров берётся из URL и пишется в URL.
- Определения колонок лежат в `columns.tsx` рядом с таблицей. `id` колонки — стабильная строковая константа, потому что на неё ссылаются URL и `localStorage`.

### 5.2. Бесконечная прокрутка и виртуализация

- Данные загружаются через `useInfiniteQuery` с курсором или смещением. Ключ включает фильтры и сортировку, но не номер страницы.
- Строки виртуализируются через `useVirtualizer`: явные `estimateSize` и `overscan`, один скролл-контейнер.
- Следующая страница запрашивается, когда последний видимый индекс подходит к концу загруженных строк. Условие: `hasNextPage && !isFetchingNextPage`.
- Таблица явно отображает каждое состояние: первая загрузка, пустой результат, ошибка с повтором, догрузка, конец списка.
- При смене фильтров прежние данные не мигают (`placeholderData: keepPreviousData`), а прокрутка сбрасывается в начало.

### 5.3. Восстановление состояния при возврате

- Фильтры и сортировка берутся из URL, поэтому при возврате получается тот же query-ключ, и загруженные страницы приходят из кэша без запроса с первой страницы.
- Прокрутка восстанавливается через scroll restoration TanStack Router, а не через ручные обработчики `scroll`:
  - в `createRouter` включается `scrollRestoration: true`;
  - скролл-контейнер списка помечается атрибутом `data-scroll-restoration-id`, тот же `id` передаётся в `useElementScrollRestoration({ id })`, а `scrollY` полученной записи — в `initialOffset` виртуализатора.
- Позиции прокрутки роутер по умолчанию восстанавливает и после перезагрузки страницы: ключ записи хранится в `history.state`, а сами позиции — в `sessionStorage`. Если после перезагрузки позиция восстанавливаться не должна, ключ делается уникальным для документа: `getScrollRestorationKey` с префиксом, который создаётся один раз при загрузке модуля. Иначе после перезагрузки виртуализатор получает `initialOffset` при ещё пустом списке, и видимая область остаётся пустой, пока пользователь не прокрутит.
- При каждом новом переходе (в том числе при смене параметров поиска) роутер сбрасывает к началу только `window` и элементы из `scrollToTopSelectors`, а позицию остальных контейнеров переносит в новую запись истории и восстанавливает после рендера. Поэтому скролл-контейнер списка добавляется в `scrollToTopSelectors` (`[data-scroll-restoration-id="<id>"]`): тогда при смене фильтров и сортировки он сбрасывается к началу, а при «назад» восстанавливается. Сбрасывать его вручную (`scrollToOffset(0)` в эффекте) **НЕЛЬЗЯ**: роутер применит сохранённую позицию позже и перезапишет сброс.

### 5.4. Настройка колонок

- Видимость, порядок и ширина колонок — это состояние TanStack Table (`columnVisibility`, `columnOrder`, `columnSizing`), которое синхронизируется с `localStorage`.
- Значение из `localStorage` проверяется Zod-схемой. Ключ хранилища содержит версию. Если данные невалидны или колонка неизвестна, используется значение по умолчанию. Ошибка доступа к хранилищу не должна ломать таблицу.

## 6. Параметры URL и фильтры

- Параметры поиска маршрута описываются Zod-схемой в `validateSearch` и имеют значения по умолчанию. Компоненты читают их только через типизированный `Route.useSearch()`.
- Некорректный параметр приводит к значению по умолчанию, а не к ошибке страницы.
- Значения по умолчанию в URL не пишутся, чтобы ссылки оставались короткими.
- Текстовый поиск пишется в URL с debounce (~300 мс) и `replace: true`. Дискретные изменения (выбор в фильтре, сортировка) создают запись в истории.
- Панель фильтров не является формой с отправкой: каждое изменение сразу меняет URL. Кнопка «Сбросить» очищает параметры.

## 7. Дизайн-система

- Токены (цвета, отступы, радиусы, шрифты) задаются в теме Ant Design через `ConfigProvider` (`theme.token`, `theme.components`). Тёмная тема включается через `theme.algorithm`.
- Цвета и размеры в компонентах берутся из `theme.useToken()`. Hex-значения и магические числа в разметке **НЕЛЬЗЯ** использовать.
- Раскладка строится на `Flex`, `Space` и `Layout`. Собственные стили пишутся в CSS Modules.
- `shared/ui` содержит обёртки над AntD без предметной логики. Компонент выносится туда, когда используется в двух и более местах.
- Каждое видимое состояние таблицы (загрузка, пусто, ошибка, данные) **нужно** покрыть интеграционным тестом (раздел 10).

## 8. Именование

| Что | Правило | Пример |
|---|---|---|
| Компонент | PascalCase, папка и файл с одним именем | `CustomerTable/CustomerTable.tsx` |

| Неиспользуемая переменная | префикс `_` | `const { id: _, ...rest } = x` |

## 9. Типизация

- `tsconfig`: `strict: true`, `noUncheckedIndexedAccess: true`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`.
- `any` **запрещён**. Для неизвестных данных используется `unknown` с проверкой через Zod.
- `as` и `!` разрешены только с комментарием, объясняющим, почему это безопасно.
- Объединения строк выводятся из константных объектов:

  ```ts
  export const CUSTOMER_STATUS = { active: "active", blocked: "blocked" } as const;
  export type CustomerStatus = (typeof CUSTOMER_STATUS)[keyof typeof CUSTOMER_STATUS];
  ```

- Импорты типов оформляются как `import type`.

## 10. Тесты

Тест пишется на каждое требование спецификации. В плане указано, какой тест покрывает какое требование.

| Уровень | Инструмент | Что проверяет |
|---|---|---|
| Unit | Vitest | Схемы URL (парсинг, значения по умолчанию, мусор на входе), преобразование URL ↔ параметры запроса, чтение настроек колонок из `localStorage` |
| Интеграционный | Vitest + Testing Library + MSW | Таблица: смена фильтра или сортировки отправляет правильные параметры, отображаются все состояния, колонки скрываются и переставляются, настройки переживают перемонтирование |
| E2E | Playwright | Прокрутка догружает страницы; переход на карточку и «назад» восстанавливает фильтры, сортировку, загруженные строки и позицию прокрутки; ссылка с параметрами открывает то же состояние |

- Элементы ищутся по роли и доступному имени (`getByRole`), а не по классам и `data-testid`. `data-testid` допускается только там, где роли нет.
- Данные детерминированы: faker с фиксированным seed, MSW-хендлеры общие с dev-режимом.
- Тесты проверяют поведение, видимое пользователю, а не внутреннее состояние компонентов и сторов.

## 11. Линтер

ESLint (flat config) в type-aware режиме, запуск с `--max-warnings 0` и `--report-unused-disable-directives`.

| Правило | Уровень | Зачем |
|---|---|---|
| `boundaries/dependencies`, `boundaries/no-unknown-files` | error | Направление импортов FSD, импорт через `index.ts` и отсутствие файлов вне слоёв проверяет машина |
| `react-hooks/rules-of-hooks`, `react-hooks/exhaustive-deps` | error | Корректность хуков |
| `@tanstack/query/exhaustive-deps` | error | Всё, что использует `queryFn`, должно входить в ключ |
| `@tanstack/query/no-rest-destructuring` | error | Без лишних подписок и ререндеров |
| `@tanstack/query/stable-query-client` | error | `QueryClient` создаётся один раз |
| `@typescript-eslint/no-explicit-any` | error | См. раздел 9 |
| `@typescript-eslint/no-floating-promises` | error | Необработанные промисы в обработчиках |
| `@typescript-eslint/consistent-type-imports` | error | Единообразные импорты типов |
| `@typescript-eslint/no-unused-vars` (игнор `^_`) | error | Мёртвый код |
| `@typescript-eslint/no-deprecated` | warn | Устаревшие API (с `--max-warnings 0` блокируют задачу) |
| `react-refresh/only-export-components` | warn | Корректный HMR |
