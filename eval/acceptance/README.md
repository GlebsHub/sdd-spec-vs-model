# Скрытая приёмка «Мои клиенты»

Playwright-тесты по критериям AC-01…AC-15 спецификации `spec/clients-table-full.md` (v1.3). Оцениваемый агент их не видит: раннер кладёт их в копию только на время прогона.

## Запуск

```
node eval/acceptance/run.mjs <папка копии> [--out result.json] [--repeat N] [--workers N]
```

Копию даёт `eval/lib/make-copy.mjs` или `eval/reference/build.mjs` (`--bare` — голая база). Раннер:

1. копирует `playwright.config.ts`, `support/`, `tests/` в `<копия>/.acceptance/` и после прогона удаляет;
2. поднимает dev-сервер копии на свободном порту (`npx vite --port N`), прогревает его (`support/warmup.ts`) и запускает тесты в Chromium: 1280×800, `ru-RU`, `Europe/Moscow`, без повторов;
3. группирует тесты по префиксу `AC-NN`: критерий прошёл, если прошли все его тесты;
4. пишет JSON и печатает сводку.

```json
{
  "copy": "/…/reference-…", "baseCommit": "…", "runs": 3, "flaky": [],
  "summary": { "passed": 15, "failed": 0, "total": 15 },
  "criteria": {
    "AC-04": { "status": "failed", "reason": "AC-04 посимвольный ввод…: Error: expect(received).toEqual(expected) | …",
               "tests": [{ "title": "…", "status": "failed", "durationMs": 1830, "error": "…" }] }
  }
}
```

При `--repeat N` критерий считается пройденным, только если прошёл во всех прогонах; `flaky` — критерии с разным результатом в разных прогонах, `perRun` — сводка по каждому прогону. Если приложение не поднялось, все AC получают `failed` с этой причиной.

## На что опираются тесты

- **Только на спецификацию:** тексты, подписи полей, роли (`table`/`grid`, `row`, `cell`/`gridcell`, `columnheader`, `combobox`, `checkbox`, `status`, `button`), `aria-sort`. Никаких `data-testid`, классов и знаний о структуре кода.
- **На контракт стенда:** флаги мока `?mock=…&mockDelay=…&mockFailTimes=…&agent=…`, журнал запросов и переключение сценария через `window.__mocks`, запросы к `/api/agent/clients` как оракул ожидаемых данных. Запросы оракула помечены параметром `__acceptance_oracle` и не попадают в проверки.
- **Скролл-контейнер** — ближайший прокручиваемый предок строки таблицы, иначе документ. Это раскладка, а не код.
- **Поле «Статус»** — `combobox` с этим доступным именем: открыть и кликнуть пункт, как пользователь мышью: видимый `option` с этим именем, иначе видимый элемент с точным текстом пункта вне таблицы и вне поля (AntD не даёт видимым пунктам роль `option`), и только в крайнем случае ввод текста и Enter. Если combobox нет — группа `checkbox` с той же подписью. Спека требует множественный выбор, а не конкретный контрол и не поиск с клавиатуры.
- **Строка данных** — строка таблицы с непустым текстом и не меньше чем двумя ячейками. Служебные строки на всю ширину (индикатор догрузки, ошибка догрузки) строками данных не считаются.
- **React StrictMode в dev-режиме** монтирует компоненты дважды, и первый запрос может уйти повторно с теми же параметрами. Там, где важно число запросов к порциям (AC-08), считаются уникальные запросы; в AC-04 и AC-07 — только запросы первой порции.

## Не проверяется автоматически

| Требование | Причина |
|---|---|
| Иконка направления сортировки в заголовке (п. 6, AC-07) | Спека не задаёт для иконки ни роли, ни текста, ни доступного имени. Любой селектор опирался бы на реализацию. Направление проверяется по `aria-sort` |
| Ручной ввод дат в поле «Период регистрации» (п. 5, AC-05) | Формат ввода и вид контрола спека не задаёт. Период проверяется через адресную строку (`from`/`to` → `dateFrom`/`dateTo`), отображение выбранных дат в поле и сброс |
| Цвет тега статуса (п. 4.2) | Цвет — дополнительный признак, задаётся токенами темы; проверяется, что статус передаётся текстом (AC-02, AC-14) |
| Внешний вид: отступы, шрифты, раскладка | Вне критериев приёмки |

## Исправления после пилота харнесса (22.10.2026)

Пилот `H-full-on` выявил два ложных падения в хелперах, сам код агента был корректен:

1. Индикатор догрузки агент вывел строкой таблицы с одной ячейкой, и хелпер принял её за строку данных (AC-09). Теперь строка данных — не меньше двух ячеек.
2. Статус выбирался вводом текста пункта; у агента, как у AntD по умолчанию, поиск шёл по коду статуса, и выбор не срабатывал (AC-05, AC-06, AC-10, AC-12). Теперь пункт кликается.

После правок повторена вся валидация (ниже). Дополнительно: эталон с поиском AntD по умолчанию (по `value`) — 15/15. Пилот переоценён `eval/harness/rescore.mjs`: 9 → 14/15.

## Исправления после круга 1 (23–26.10.2026)

Подробности, проверка и влияние на результаты — [docs/acceptance-changes.md](../../docs/acceptance-changes.md), правки 3–6.

3. AC-01: строки скелетона считаются как строки таблицы без `columnheader` (`nonHeaderRows`), ячейки в них не требуются — спека говорит только о «скелетоне таблицы на 10 строк».
4. AC-15: предусловие «загружены все порции» считает уникальные успешные запросы — StrictMode в dev повторяет первый запрос.
5. Харнесс оценивает прогон по большинству из трёх повторов приёмки (`eval/harness/lib/score.mjs`); сам раннер по-прежнему засчитывает AC при `--repeat N`, только если тот прошёл во всех повторах.
6. Выбор статуса ждёт до 5 с, пока пункт списка отрисуется: сразу после клика по полю его ещё нет, и хелпер уходил в ввод с клавиатуры.
