# План: базовый проект `base/`

Статус: **реализовано** 22.10.2026. Решения по вопросам — в разделе 5, отклонения от плана — в разделе 7.

Принцип для всех решений: в `base/` есть только инфраструктура, перечисленная в задаче. Всё, что напрямую закрывает критерии приёмки (AC-xx), агент делает сам: `staleTime` 60 с, scroll restoration, `validateSearch`, хуки, таблица, настройки колонок. Так базовый проект одинаков для всех прогонов и не подсказывает решение.

## 3. Ключевые решения

### 3.1. Роутер
Дерево маршрутов задаётся в коде (`app/router.tsx`), без file-based плагина и кодогенерации: `tsc --noEmit` работает без шага генерации, у агента меньше скрытых механизмов. Страницы читают параметры через `getRouteApi('/clients')`, потому что импортировать `Route` из `app` слой `pages` не может. Маршруты: `/` → редирект на `/clients`, `/clients`, `/clients/$clientId`, 404.

Кнопка «Назад» в карточке: если в истории есть куда вернуться, `history.back()`, иначе переход на `/clients`.

### 3.2. shared/api
- `ClientListResponseSchema` ровно по п. 3.1: `id` uuid, `status` из `CLIENT_STATUS` (`as const`), `registeredAt` ISO datetime, `commissionKopecks` и `productsCount` целые ≥ 0, `nextCursor` `string | null`, `total` целое ≥ 0.
- Схему параметров запроса не пишу. Это преобразование URL → запрос, оно входит в фичу. В базе только константы допустимых значений `sort`.
- http-клиент: `get(path, { params, schema, signal })`. `params: Record<string, string | number | undefined>`, `undefined` не передаётся. Массив в строку через запятую собирает вызывающий код, потому что это часть контракта, а не HTTP. Не-2xx → `HttpError` со `status`, сбой fetch → `NetworkError`, ответ не по схеме → `ContractError` с причиной от Zod. По этим классам фича отличит 403 от остальных ошибок.
- `clientKeys`: `all`, `lists()`, `list(params)`, `detail(id)`. `params` типизирован через дженерик, тип параметров списка агент определит сам.

### 3.3. formatMoney
Только целочисленная арифметика по копейкам, без `Intl` и деления на 100 в float: рубли — `Math.trunc(k / 100)`, копейки — `k % 100`, группировка по 3 цифры, `U+00A0` между разрядами и перед `₽`. Не safe integer → `RangeError`. Тесты: `1234567`, `0`, `5`, `100`, `99`, `100000000`, граница `MAX_SAFE_INTEGER`, дробное → ошибка, отрицательные (см. В5).

### 3.4. QueryClient
Явные нейтральные значения: `staleTime: 0`, `gcTime: 10 мин`, `retry: false`, `refetchOnWindowFocus: false`. `retry: false` нужен, чтобы сценарии ошибок проявлялись сразу и детерминированно; повтор в спеке делается кнопкой «Повторить». 60 с из п. 9.2 агент задаёт сам в `queryOptions`. Глобальный обработчик 401 (вне рамок раздела): `QueryCache.onError` для `HttpError` 401 показывает `notification`.

### 3.5. Мок-бэкенд
**Где.** `src/mocks/` вне слоёв FSD, как и `src/test/`. Импортировать его можно только из `main.tsx`, `src/test` и тестов, это проверяет линтер. Конвенция «`mocks.ts` в сущности» в `base/conventions.md` меняется: мок-бэкенд готовый, агент его не меняет. Свои фабрики данных для юнит-тестов ему писать можно.

**Данные.** `createClientsDb(seed)`: чистая функция, 10 000 записей, faker `ru`, фиксированный seed.
- ФИО в порядке «Фамилия Имя Отчество», согласованное по полу.
- `phoneMasked` в формате `+7 *** ***-XX-XX`.
- Статусы с правдоподобным распределением.
- `registeredAt` за 3 года до фиксированной даты 2026-10-01, без `Date.now()`. Время только 06:00–18:00 UTC, чтобы дата совпадала в UTC и в МСК (см. В4).
- `commissionKopecks`: у `LEAD` 0. Детерминированно есть записи с 0, 5 и 1234567 копеек.
- `productsCount` 0–5.
- Есть несколько «Иванов…» для AC-04.

**Контракт.** Мок строгий: нарушение контракта видно сразу.
- `limit`: обязателен, целое 1–100, иначе 400.
- `q`: после trim короче 2 символов → 400. Поиск без учёта регистра по подстроке ФИО.
- `status`: только через запятую. Неизвестное значение или повтор параметра → 400.
- `dateFrom` / `dateTo`: `YYYY-MM-DD`, включительно, сравнение по дате UTC. Неверный формат → 400.
- `sort`: `поле:направление`, по умолчанию `registeredAt:desc`. Неверное значение → 400. Вторичный ключ `id`, чтобы порядок был стабильным. `fullName` сравнивается через `localeCompare('ru')`.
- `cursor`: непрозрачный base64 с `offset` и хешем фильтров и сортировки. Курсор от другого набора фильтров или битый → 400. Так ловится ошибка «курсор от старых фильтров».
- Ответ: `items`, `nextCursor` (`null` на последней порции), `total` с учётом фильтров.

**Сценарии.** Включаются URL-флагом при загрузке, например `?mock=error-next-page&mockDelay=800`. Флаги сохраняются в `sessionStorage`, поэтому переживают перезагрузку и навигацию внутри приложения. В тестах сценарий переключают программно: `setMockScenario(...)`, в dev то же доступно как `window.__mocks`.

| Сценарий | Поведение |
|---|---|
| `default` | обычная работа |
| `mockDelay=<мс>` | задержка ответа, сочетается с любым сценарием |
| `error-first-page` | 500 на запросы без `cursor` |
| `error-next-page` | 500 на запросы с `cursor` |
| `empty` | у агента 0 клиентов: `total: 0` при любых фильтрах |
| `forbidden` | 403 |
| `network-error` | сетевой сбой (дополнительно, есть в п. 3.1 спеки) |
| `malformed` | ответ 200 не по схеме (дополнительно, п. 3.1) |

У ошибочных сценариев есть параметр `failTimes=N`: после N ошибок ответы снова нормальные. Это нужно для проверки «Повторить», в том числе для «повторяет только догрузку».

**Журнал запросов.** `getRequestLog()` / `clearRequestLog()`: распарсенные параметры каждого запроса. Пригодится скрытым тестам, например AC-04 «ровно один запрос».

### 3.6. Текущий агент
Для AC-13 («настройки отдельно для каждого агента») приложению нужна личность агента, в спеке её нет. Предлагаю `shared/lib/session`: `useCurrentAgent(): { id, name }`. Значение синхронное, задаётся при старте из флага `?agent=<id>` (тоже сохраняется в `sessionStorage`), по умолчанию `agent-1`. В тестах задаётся через `renderApp({ agentId })`. Внутри небольшой Zustand-стор. См. В3.

### 3.7. Тема
`shared/ui/theme`: `ConfigProvider` theme с токенами статусов. Имена из спеки с дефисами в объект токенов AntD не ложатся, поэтому делаю camelCase через расширение типа `AliasToken`: `colorStatusNeutral`, `colorStatusInfo`, `colorStatusSuccess`, `colorStatusMuted`. В компонентах значения доступны через `theme.useToken()`. В JSDoc рядом указано соответствие `status-neutral` ↔ `colorStatusNeutral`. Компонент тега статуса не делаю: он предметный, это работа агента. Тёмную тему не включаю.

### 3.8. Линтер
Все правила из раздела 11 conventions. `@nx/enforce-module-boundaries` заменяет `eslint-plugin-boundaries`:
- направление `app → pages → widgets → features → entities → shared`;
- запрет импортов между слайсами одного слоя, кроме `import type` между сущностями;
- импорт слайса только через `index.ts`;
- `src/mocks` и `src/test` закрыты для продового кода.

Дополнительно `--report-unused-disable-directives`. Правило «`eslint-disable` только с комментарием» закрывает `@eslint-community/eslint-plugin-eslint-comments` (`require-description`) — это ещё одна зависимость. Для `as` и `!` с комментарием надёжного правила нет, остаётся текстовым требованием.

Проверю, что линтер реально ловит нарушения: временный файл с нарушением → ошибка → файл удаляю.

## 4. Противоречия между conventions.md, спекой и задачей

Правило из conventions.md: при расхождении приоритет у спеки. Задачу стенда я ставлю выше обоих.

| # | conventions.md | Спека / задача | Решение |
|---|---|---|---|
| П1 | Nx-монорепо, слайсы как библиотеки, `@nx/enforce-module-boundaries` | Задача: без Nx | `eslint-plugin-boundaries` с теми же ограничениями; в `base/conventions.md` раздел 2.2 переписан |
| П2 | Storybook: story на каждый компонент `shared/ui` и каждое состояние таблицы | Задача: без Storybook | Требование убрать. Состояния таблицы покрываются интеграционными тестами (они и так требуются в разделе 10) |
| П3 | Готовность = tsc + eslint + vitest + **playwright** | Задача: `check` = tsc + eslint + юнит-тесты | `check` без e2e, `test:e2e` отдельно. См. В2: что считать готовностью для агента |
| П4 | Схемы, типы, query-ключи — в `entities/<x>/schema.ts`, `queries.ts`. `shared` без предметной логики | Спека п. 3.1 и задача: схема и фабрика ключей в `shared/api` | Как в спеке: `shared/api/clients/`. В `base/conventions.md` записываю исключение: контракты API лежат в `shared/api`, сущность их реэкспортирует и добавляет `queryOptions` и хуки |
| П5 | MSW-хендлеры в `mocks.ts` сущности, их пишет разработчик | Задача: мок-бэкенд готовый, в базе | `src/mocks/` вне слоёв; агенту менять нельзя (п. 3.5) |
| П6 | Колонки: видимость, **порядок и ширина** в `localStorage` | Спека: порядок фиксированный, изменение порядка вне рамок; ширина не упоминается | Приоритет у спеки: только видимость. В `base/conventions.md` не меняю, это ситуация «спека важнее» и проверяет, заметит ли её агент |
| П7 | Реализация «снизу вверх: схема → API и моки → …» | Схема и моки уже есть | Агент начинает с запросов. Формулировку не меняю |
| П8 | Фабрика ключей `customerKeys`, примеры на `customer` | Предметная область — `client` | Имена `clientKeys`, `ClientSchema`. Примеры в conventions оставляю как есть |

Расхождения внутри спеки, которые агенту придётся заметить самому; в базе их не решаю:
- имена параметров URL `from` / `to` и API `dateFrom` / `dateTo` разные. Это не ошибка, но маппинг нужен явный;
- дата регистрации показывается в часовом поясе пользователя, а у фильтра по дате часовой пояс не указан (В4).

## 5. Вопросы

**В1. Свежие мажоры.** TanStack Table 9.0 вышла 04.08.2026, MSW 3.0 — 28.09.2026. «Актуальная стабильная» — это они. Но модели в основном знают API Table v8 и MSW v2. Итог прогона будет зависеть ещё и от того, знает ли модель новый API, и это смешается с переменными гипотезы (модель × спека × контур проверок).
Варианты:
(а) последние версии, разницу знаний считаем частью эксперимента;
(б) **рекомендую:** Table 8.21.3 и MSW 2.x последней версии, причину записать в CLAUDE.md.
MSW агент почти не трогает, поэтому для него разница небольшая. Table — ядро фичи.

**В2. Критерий готовности для агента.** В контур проверок, который виден агенту, входит только `npm run check` или ещё `test:e2e`? От этого зависит, что значит «с контуром проверок / без» в харнессе. Предлагаю так: «с контуром» — агенту разрешено запускать `check` и `test:e2e`, а в CLAUDE.md сказано, что готовность = оба зелёные; «без» — команды не упоминаются и запрещены. Решим при сборке харнесса, но `base/CLAUDE.md` зависит от этого уже сейчас. Пока пишу версию «с контуром», харнесс потом подставит вариант.

**В3. Личность агента для AC-13.** Устраивает синхронный `useCurrentAgent()` из флага `?agent=`? Альтернатива — эндпоинт `GET /api/agent/me` с хуком, но тогда появляется лишнее состояние загрузки, которого нет в спеке.

**В4. Часовой пояс фильтра по дате.** В моке сравниваю по дате UTC, а данные генерирую так, чтобы дата в UTC и в МСК совпадала. Playwright запускается с `timezoneId: 'Europe/Moscow'`. Устраивает? Или зафиксировать часовой пояс в спеке (тогда версия спеки 1.2)?

**В5. formatMoney для отрицательных.** Спека задаёт комиссию ≥ 0. Отрицательное число: `RangeError` или `−12,34 ₽`? Рекомендую `RangeError`: утилита не обещает больше, чем говорит спека.

**В6. Подсказки в базе.** Сценарии мока (`empty`, `forbidden`, `error-next-page`), токены статусов и `formatMoney` раскрывают детали полной спеки агенту с краткой спекой. Полностью этого не избежать: код лежит в базе. Варианты:
(а) **рекомендую:** не описывать сценарии в `base/CLAUDE.md`, только в комментариях `src/mocks/scenarios.ts`;
(б) описать в CLAUDE.md, чтобы агент мог сам проверить состояния.
Сейчас делаю (а).

**В7. Куда кладётся спека.** Под каким именем харнесс кладёт спеку в копию базы? Предлагаю `SPEC.md` в корне копии, `base/CLAUDE.md` ссылается на него.

**В8. Корневой conventions.md.** Перенести его в `base/conventions.md` (`git mv`) с правками П1–П3 и П5, чтобы был один источник? Или оставить оригинал в корне как исходник, а в `base/` положить адаптированную копию? Рекомендую перенести: две версии разойдутся.

**В9. Защита инфраструктуры.** Агенту запрещено менять `src/mocks`, `src/test`, `shared/api/clients/schema.ts` и конфиги линтера и TS. Писать это только в `base/CLAUDE.md` или харнесс ещё будет сверять контрольные суммы после прогона? Второе потом проверяет харнесс, но правило в CLAUDE.md пишу в любом случае.

## 6. Проверка после реализации
1. `npm ci` с нуля → `npm run check` зелёный.
2. Проверка линтера на нарушениях: импорт вверх по слоям, глубокий импорт, `any`, floating promise, `eslint-disable` без описания → каждое ловится.

## 2.2. Восстановление прокрутки: что проверено

Проверял по исходникам установленной `@tanstack/react-router` 1.170.45 (`router-core/src/scroll-restoration.ts`) и по гайду Scroll Restoration на tanstack.com (latest).

Подтверждено:
- `useElementScrollRestoration({ id })` + `initialOffset: entry?.scrollY` у виртуализатора — это и есть документированный способ для виртуализированных списков. Суть правила §5.3 верна.

Чего в правиле не хватает:
1. **Опция роутера `scrollRestoration: true` в `createRouter`.** Гайд включает восстановление именно так. Хук сам вызывает `setupScrollRestoration(router, true)`, поэтому без опции работает, но это недокументированная зависимость.
2. **Атрибут `data-scroll-restoration-id`** на скролл-контейнере, с тем же `id`, что в хуке. Без атрибута роутер запоминает элемент по CSS-пути `nth-child`, а хук с `id` ищет запись по атрибуту, и они не совпадают.
3. **Перезагрузка — конфликт со спекой.** Ключ кэша — `location.state.__TSR_key`. Он хранится в `history.state` и переживает перезагрузку. Кэш позиций на `pagehide` сохраняется в `sessionStorage` и читается при загрузке модуля роутера. Значит, по умолчанию после перезагрузки позиция восстанавливается, а спека 9.2 требует обратного. Как спасает случай: после перезагрузки данных ещё нет, высота контейнера маленькая, и `scrollTop` упирается в 0. На это полагаться нельзя: если скелетон высокий, а `initialOffset` применяется при создании виртуализатора, позиция может частично восстановиться.
4. **Сброс к началу при смене фильтров.** Роутер сбрасывает к началу только `window` и элементы из `scrollToTopSelectors`. Скролл-контейнер таблицы сам по себе не сбросится. Нужно либо добавить его в `scrollToTopSelectors`, либо явно вызывать `scrollToOffset(0)`. Явный вызов надёжнее: при `replace: true` от поиска тоже нужен сброс.

**Эксперимент (выполнен).** Одноразовый прототип в копии базы: виртуализированный список, `useInfiniteQuery` с `staleTime` 60 с и `keepPreviousData`, восстановление по гайду. Chromium, Playwright.

| Случай | Результат по гайду | С ключом, уникальным для документа |
|---|---|---|
| Прокрутка 6000 → карточка → «назад» браузера | 6000 → 6000 | 6000 → 6000 |
| Прокрутка 3000 → карточка → кнопка «Назад» | 3000 → 3000 | 3000 → 3000 |
| Прокрутка 3000 → перезагрузка, задержка ответа 300 мс | **`scrollTop` 0, но виртуализатор рисует строки с 65-й: видимая область пустая** | `scrollTop` 0, видна строка 0 |
| Прокрутка 1500 → смена фильтра (`keepPreviousData`) | **остаётся 1500** | остаётся 1500; см. уточнение ниже |
| Без `data-scroll-restoration-id` | «назад» работает: роутер находит элемент по CSS-пути `nth-child`. Этот путь ломается при любом изменении разметки, поэтому атрибут остаётся обязательным | — |

Предположение про `performance.getEntriesByType("navigation")` не подходит: тип `reload` сохраняется за документом, и последующие переходы «карточка → назад» тоже выглядели бы как перезагрузка. Ключ с префиксом документа решает задачу одной опцией роутера: `` getScrollRestorationKey: (l) => `${DOCUMENT_ID}:${l.state.__TSR_key ?? l.href}` ``.

**Уточнение при реализации эталона.** Явный `scrollToOffset(0)` в эффекте при смене параметров не работает. При новом переходе роутер копирует позиции элементов, не входящих в `scrollToTopSelectors`, из прежней записи истории в новую и в `onRendered` возвращает их, то есть после эффекта: замер — 1908 → 1908. Если контейнер указан в `scrollToTopSelectors`, роутер сам сбрасывает его при новом переходе (1908 → 0), а при «назад» восстанавливает. Формулировка §5.3 из коммита `77c1e23` про явный сброс была неверной и исправлена.

**Правка §5.3 `base/conventions.md`.** Правило было верным по сути, но неполным, и буквальное следование ему давало ошибку после перезагрузки. Добавлено: опция `scrollRestoration: true`; атрибут `data-scroll-restoration-id` с тем же `id`, что в хуке; ключ, уникальный для документа, если позиция не должна переживать перезагрузку; контейнер в `scrollToTopSelectors` для сброса при смене фильтров и сортировки, а ручной сброс запрещён.

## 2.4. Приёмочные тесты

**Где запускаются.** Все AC — в Playwright, включая те, что формально можно проверить в jsdom (вопрос Э1). Причина: любая проверка таблицы в jsdom упирается в виртуализацию. Строки рендерятся, только если подменить размеры элементов, а как подменять, зависит от реализации (`getBoundingClientRect`, `offsetHeight`, `ResizeObserver`). Скрытый тест, который зависит от реализации, нарушает требование «никаких знаний о структуре кода».

**Окружение.** Chromium, 1280×800, `locale: ru-RU`, `timezoneId: Europe/Moscow`, `retries: 0`. Свой dev-сервер на свободном порту: `npx vite --port <N>`, `strictPort` из конфига копии не мешает.

**Что можно использовать в селекторах.** Тексты, подписи полей, роли и aria-атрибуты из спеки. Отдельно:
- Строки данных — `row`, в которой есть `cell`.
- Скролл-контейнер — ближайший прокручиваемый предок строки, находится вычислением стилей. Это знание о раскладке, а не о коде.
- Мок-бэкенд: флаги `?mock=…`, `window.__mocks.getRequestLog()` и `fetch` к `/api/agent/clients` как оракул ожидаемых данных. Это контракт стенда, не код фичи.

**Раннер `run.mjs <копия> [--out file] [--repeat N]`.**
1. Копирует `eval/acceptance` в `<копия>/.acceptance/` (оттуда видны `node_modules` копии), запускает Playwright с JSON-репортером и после прогона удаляет папку.
2. Группирует тесты по префиксу `AC-NN`. AC прошёл, если прошли все его тесты.
3. Пишет JSON:
   ```json
   { "copy": "...", "baseCommit": "...", "startedAt": "...", "durationMs": 0,
     "summary": { "passed": 0, "failed": 15, "total": 15 },
     "criteria": { "AC-01": { "status": "failed", "reason": "первая строка ошибки",
   ```

4. Если dev-сервер не поднялся или упала компиляция, все AC `failed` с этой причиной; раннер не падает.
5. `--repeat N` прогоняет N раз и помечает нестабильные тесты, нужно для валидации.

## 2.5. Валидация

1. Эталон: `run.mjs --repeat 3` — все 15 AC зелёные во всех трёх прогонах.
2. Голая база: все 15 красные. Если что-то зелёное, тест исправляю: ищу проверки, которые проходят без фичи. Типичный случай — «кнопка не видна» без положительной части.
3. Мутационная проверка, дополнительно: 3–4 правки эталона, каждая ломает ровно один AC. Например, убрать `staleTime` → AC-11; убрать debounce → AC-04; убрать виртуализацию → AC-15. Должен покраснеть именно этот AC. Так видно, что тесты ловят нарушения, а не только отсутствие фичи. Мутации временные, в репозиторий не идут.

**Э4.** Правка §5.3 conventions по итогам п. 2.2 меняет коммит базы. Делаю отдельным коммитом до эталона, чтобы эталон и приёмка собирались на финальной базе?

## 2.7. Итог этапа

Решения: Э1 — все AC в Playwright; Э2 — AC-12 проверяет и отсутствие восстановления прокрутки после перезагрузки; Э3 — хелпер по ролям (combobox → пункт, иначе группа чекбоксов); Э4 — правка conventions отдельным коммитом до эталона. Спека 1.3: индикатор догрузки «Загружаем ещё…» с ролью `status`, проверяется в AC-09.

Коммиты базы на этапе:

| Коммит | Что |
|---|---|
| `77c1e23` | Спека 1.3; §5.3 conventions по результатам эксперимента |
| `8c1047c` | Дефект базы: обёртка AntD `App` без высоты, `height: 100%` ниже неё не работал, ограниченный скролл-контейнер страницы был невозможен. Найдено при сборке эталона: таблица растягивалась на всю высоту, виртуализация не работала |
| `541a56f` | Исправление §5.3: ручной `scrollToOffset(0)` перезаписывается роутером, контейнер должен быть в `scrollToTopSelectors` (см. п. 2.2). `formatMoney`: невидимый U+00A0 в исходнике заменён на `\u00A0` |

Что нашлось по ходу и как решено:
- **Эталон, поиск статуса.** AntD `Select` по умолчанию ищет пункты по `value` (`FUNDED`), а не по подписи, поэтому ввод «Пополнил» ничего не находил. В эталоне `showSearch={{ optionFilterProp: "label" }}`.
- **StrictMode в dev.** Двойное монтирование отменяет первый запрос, переданный с `signal`, и отправляет его повторно. Это не дефект реализации, поэтому приёмка считает уникальные запросы (AC-08) или только запросы первой порции (AC-04, AC-07).
- **Эквивалентный мутант.** Ключ прокрутки без префикса документа у эталона не ломает поведение после перезагрузки: сначала рендерится скелетон, и виртуализатор при монтировании синхронизируется с реальной позицией 0. В прототипе без скелетона та же ситуация давала пустую видимую область. Правило §5.3 оставлено как защитное. AC-12 проверяет и позицию, и видимость первой строки, то есть ловит оба варианта ошибки.

Валидация — в `eval/acceptance/README.md`: эталон 15/15 ×3 без флаков, голая база 0/15 (0 из 36 тестов), шесть мутаций — каждая красит ровно свой AC.

Эталон в цифрах: 34 файла в `eval/reference/files/`, в копии 76 тестов Vitest (юнит + интеграция) и 4 e2e своих плюс smoke базы; `check` и `test:e2e` зелёные.

## 2.8. Для отчёта

### Чувствительность приёмки: поломка → красный AC

Каждая поломка — временная правка эталона в одну строку. Приёмка запускалась целиком, красным становился ровно один критерий.

| Поломка эталона | Нарушенное требование | Красный AC |
|---|---|---|
| `staleTime` 0 вместо 60 с | п. 9.2: при возврате в пределах 60 с — без повторного запроса | AC-11 |
| debounce поиска 0 вместо 300 мс | п. 5: запрос через 300 мс после последнего ввода | AC-04 |
| запас строк виртуализатора 100 вместо 10 | п. 8: не более 10 строк запаса | AC-15 |
| у индикатора догрузки нет `role="status"` | п. 7 (v1.3): индикатор с ролью `status` | AC-09 |
| догрузка запускается снова после ошибки | п. 7: после ошибки — только по кнопке «Повторить» | AC-09 |
| контейнер таблицы не в `scrollToTopSelectors` | п. 5: смена фильтров и сортировки прокручивает к началу | AC-06 |

Контроль: на эталоне 15/15 в трёх прогонах подряд без флаков; на голой базе 0/15, ни один из 36 тестов не проходит.

### История правила прокрутки (conventions §5.3)

1. **Исходное правило:** «прокрутка восстанавливается через `useElementScrollRestoration` и `initialOffset` виртуализатора, без ручных обработчиков `scroll`». По сути это верно и совпадает с гайдом TanStack Router, но правило неполное.
2. **Проверка по исходникам роутера 1.170.45.** Найдено: нужна опция `scrollRestoration: true`; нужен атрибут `data-scroll-restoration-id`; позиции хранятся в `sessionStorage` под ключом из `history.state`, поэтому по умолчанию переживают перезагрузку, а спека 9.2 требует обратного.
3. **Эксперимент в Chromium на прототипе** (`77c1e23`). «Назад» восстанавливает позицию точно. После перезагрузки получается `scrollTop` 0, но виртуализатор рисует строки с 65-й, и видимая область пустая. Добавлено правило про ключ, уникальный для документа. Здесь же записано ошибочное правило: сбрасывать контейнер при смене фильтров явным `scrollToOffset(0)`.
4. **Эталон опроверг явный сброс** (`541a56f`). При новом переходе роутер переносит позицию контейнера в новую запись истории и применяет её в `onRendered`, после эффекта компонента: замер 1908 → 1908. Верный способ — контейнер в `scrollToTopSelectors`: 1908 → 0 при смене сортировки, и восстановление при «назад» сохраняется. Ручной сброс в conventions теперь запрещён.
5. **Мутационная проверка.** Ключ без префикса документа у эталона поведение не меняет: сначала скелетон, и виртуализатор синхронизируется с позицией 0. Правило осталось защитным, AC-12 ловит оба варианта ошибки — восстановленную позицию и пустую видимую область.

Вывод для отчёта: правило в conventions, которое агент выполнил бы буквально, дважды требовало проверки на работающем коде. Первая версия была неполной, исправление к ней — ошибочным. Обе ошибки нашлись только при запуске в браузере, а не при чтении документации.

## 3.3. Один прогон

1. **Копия.** `makeCopy({ commit: "541a56f", spec })` в `$TMPDIR/sdd-eval-runs/<config>-<n>-<время>/`. Это отдельная папка, не та, где лежат копии эталона (п. 3.4б).
2. **Вариант `CLAUDE.md`.** Для «без контура» вырезается блок между маркерами `contour`; базовый коммит копии переписывается, чтобы дифф агента считался от того, что он увидел. Для «без контура» дополнительно ставятся заглушки проверок (п. 3.5).
3. **Контрольные суммы «до»** — sha256 защищённых путей из `eval/lib/protected.mjs`.
4. **Агент:**
   ```
   claude -p "Реализуй SPEC.md, следуя CLAUDE.md" --model <id> --effort <уровень> \
     --output-format stream-json --verbose --max-turns 300 --permission-mode bypassPermissions \
     --settings <настройки прогона> --strict-mcp-config --mcp-config '{"mcpServers":{}}' \
     --disable-slash-commands --no-session-persistence
   ```
   - CLI запускается в своей группе процессов, `cwd` — копия.
   - Лимит **25 минут** по часам харнесса: SIGTERM группе процессов, через 10 с SIGKILL.
   - Затем добиваются процессы, оставленные агентом: dev-серверы и всё, что слушает 5173 из папки копии.
5. **Контрольные суммы «после».** Любое расхождение — изменён, удалён или переименован защищённый файл — значит `protectedViolation: true`, прогон — провал. Дальше всё выполняется как обычно.
6. **Приёмка:** `eval/acceptance/run.mjs <копия>`. Перед ней заглушки «без контура» снимаются.
7. **Скриншоты** (п. 3.6) и **сбор артефактов** (п. 3.7).
8. **Копия удаляется.** С `--keep` остаётся для разбора.

## 3.4. Честность и изоляция

**а. Личная конфигурация не должна попасть в прогоны.** Сейчас Claude Code подхватывает мои `~/.claude`: пользовательский CLAUDE.md, память, skills, плагины, MCP-коннекторы claude.ai (Claude Docs и др.). Они меняют поведение и токены. Решение:
- `CLAUDE_CONFIG_DIR` — чистая папка на каждый прогон;
- авторизация — долгоживущим OAuth-токеном подписки (`claude setup-token`, переменная `CLAUDE_CODE_OAUTH_TOKEN`), без API-ключа;
- плюс `--strict-mcp-config` с пустым списком и `--disable-slash-commands`.

Пилот проверяет по событию `system/init`: в списке инструментов нет MCP и skills, CLAUDE.md только проектный. См. вопрос Х2.

**б. Скрытые тесты и эталон не должны быть доступны.** С `bypassPermissions` агент технически может прочитать любой файл: репозиторий с `eval/acceptance` и `eval/reference`, а также `$TMPDIR/sdd-eval/reference-*`. Меры:
- прогоны идут в отдельной папке `sdd-eval-runs/`, старые копии эталона харнесс удаляет перед кругом;
- в настройках прогона запрет `Read`/`Glob`/`Grep` на путь репозитория и `sdd-eval/`, для Bash — песочница Claude Code с запретом чтения тех же путей;
- после прогона харнесс ищет в логе пути репозитория, `acceptance`, `reference` и ставит `leakSuspect`. Такой прогон помечается и разбирается вручную.

**в. Порт 5173 и параллельность.** Порт агента зашит в защищённые `vite.config.ts` (`strictPort`) и `playwright.config.ts`. Отдельный порт агенту не дать, не меняя базу. Хуже того, локально Playwright с `reuseExistingServer` молча подключится к dev-серверу соседнего прогона и проверит чужой код.
- `--parallel N` разведёт по портам только серверы харнесса (приёмка, скриншоты), но не агентов.
- Поэтому **рекомендую только последовательные прогоны.** `--parallel` реализую, но для конфигураций «с контуром» он откажется запускаться, а для «без контура» выведет предупреждение.
- Перед каждым прогоном харнесс проверяет, что 5173 свободен.

**г. Лимиты подписки Pro.** Круг — до 5 × 25 минут работы агента, Sonnet тратит больше. Если лимит закончится посреди прогона, результат будет искажён. Харнесс распознаёт такие случаи — ошибка API 429, сообщение о лимите, `subtype` ошибки в `result` — и ставит статус `infra_error`. Такой прогон не входит в сводку и перезапускается при продолжении. См. вопрос Х4.

**д. Порядок внутри круга.** Круги идут в разное время суток и в разные дни. Чтобы время не смешивалось с конфигурацией, круг k начинается с k-й конфигурации (циклический сдвиг), и каждая конфигурация бывает в начале, середине и конце.

## 3.5. «Без контура»: как отключить проверки

Блок с командами вырезан из `CLAUDE.md`, но агент может догадаться сам: в `package.json` есть `check`, а `npx vitest` никто не запрещает. Два слоя:

1. **Заглушки в копии.** Ссылки `node_modules/.bin/{tsc,eslint,vitest,playwright}` подменяются скриптом: «Команда недоступна в этой конфигурации», код 1, плюс запись в журнал попыток вне копии.
   - Через эти бинарники идут `npm run check`, `test`, `test:e2e`, `lint`, `typecheck`, `npx …` и вызовы из `package.json`.
   - `node_modules` копии — APFS-клон, база не страдает. `package.json` не трогаем: он защищён.
   - Перед приёмкой ссылки восстанавливаются.
2. **Хук PreToolUse на Bash** в настройках прогона. Он отклоняет команды с `tsc`, `eslint`, `vitest`, `playwright`, `npm (run )?(check|test|lint|typecheck)`, а также прямые вызовы `node_modules/(typescript|eslint|vitest|@playwright)/…`. Ловит обходы мимо `.bin`.

Остаётся разрешённым: `npm run dev`, `curl`, чтение кода, ошибки сборки Vite. Это не автоматические проверки, а обычная ручная разработка. Метрика `blockedCheckAttempts` — сколько раз агент пытался запустить проверки — тоже интересна для отчёта.

Пилот проверяет ещё одно: не подмешивает ли CLI сам диагностику TypeScript (LSP) после правок. Если подмешивает, в «без контура» это частичный контур проверок; вынесу на решение.

- Прогон считается готовым, если в его папке есть `result.json` со статусом `complete` или `timeout`. Такие пропускаются.
- `infra_error` и незавершённые папки (харнесс прерван) переносятся в `eval/results/_aborted/` и запускаются заново. Прогон атомарен: продолжить сессию агента нельзя и не нужно.
- Харнесс пишет прогресс в `harness.log`. Ctrl+C корректно останавливает текущий прогон и помечает его `infra_error`.

## 3.10. Сводка `summarize.mjs`

Читает все `eval/results/<config>/<run>/result.json` (без `_pilot` и `_aborted`) и работает на любом числе завершённых кругов. По каждой конфигурации:

- `n` прогонов. Если их меньше 3, это отмечается;
- **средняя доля AC** (`acPassed/15`; прогон с нарушением защиты считается за 0, сырое значение тоже сохраняется), минимум–максимум и стандартное отклонение;
- **принятые прогоны**: 15/15 и без нарушения защиты;
- токены (среднее по вход / выход / запись кэша / чтение кэша, отдельно фоновая модель), время, ходы, средняя стоимость прогона;
- **условная стоимость принятого результата** = сумма стоимости всех прогонов конфигурации / число принятых. Если принятых нет, стоимость не считается и в таблице стоит «—». Дополнительно — стоимость одного пройденного AC: сумма стоимости / сумма пройденных AC. Эта метрика определена всегда и полезна, когда принятых мало;
- матрица «конфигурация × AC»: как часто проходит каждый критерий.

Выход: `eval/results/summary.json` и `eval/results/summary.md`.

## 3.11. Пилот (сегодня, до круга 1)

1. **Подготовка.** Вы один раз выполняете `claude setup-token` и кладёте токен в `eval/harness/.env.local` (в `.gitignore`).
2. **Пилот А:** `H-full-off`, `--max-turns 5`. Проверяет:
   - соблюдается ли лимит ходов (`terminalReason`);
   - изоляцию по `system/init`: инструменты, MCP, память;
   - заглушки и хук, если агент успеет попытаться;
   - разбор метрик, приёмку и скриншоты на незавершённой работе, состав артефактов.
3. **Пилот Б:** `H-full-on`, `--time-limit 3m`. Проверяет путь таймаута, добивание процессов, освобождение 5173, токены без финального события.
4. **По итогам** поправлю харнесс, пилоты останутся в `_pilot/`, затем круг 1: 5 прогонов, до ~2,5 ч.

## 3.12. Вопросы

**Х1. Уровень effort.** Харнесс должен его фиксировать. По умолчанию у Haiku 5.5 `medium`, у Sonnet 5.5 `high`, а Claude Code может выставлять свой. Рекомендую явно задать `--effort high` обеим моделям: одинаковые условия, воспроизводимо, записывается в `result.json`. Альтернатива — «как есть по умолчанию в CLI», то есть сравнение продукта, а не модели.

**Х2. Изоляция от личной конфигурации через `claude setup-token` + чистый `CLAUDE_CONFIG_DIR`.** Нужно ваше действие один раз. Без этого в прогоны попадут ваши `~/.claude`, память и MCP-коннекторы.

**Х3. Определение «принятого результата».** Рекомендую 15/15 AC и без нарушения защиты, при нарушении доля AC считается за 0. Альтернатива — порог, например ≥ 13/15.

**Х4. Подписка Pro.** Пять прогонов по 25 минут, из них Sonnet, вероятно, упрутся в лимиты использования. Харнесс переживёт это корректно (`infra_error` → перезапуск), но круг может растянуться. Устраивает или планируем круги с паузами?

**Х5. Результаты в git.** Коммитить `eval/results/` целиком, логи в `.gz` (ожидаю единицы МБ на прогон), или логи держать вне репозитория?

**Правки харнесса после круга 1** (приёмка не менялась):
